# Proofs, Attestation and Logs: What a Verifier Must Trust to Know a Safety Classifier Ran

Abdelhamid Bakhta, Lucid Computing (corresponding author)

## Abstract

Safety classifiers screen prompts and answers in many language-model services, yet users and auditors cannot check that the declared classifier produced the declared verdict on their request. We systematize operator-supplied evidence (self-report, black-box testing, replay, signed or logged records, statistical and refereed checks, hardware attestation, cryptographic proofs) by the trust elements each needs, and compare their trust sets by inclusion. Above the operator-reliant bottom class most classes are incomparable, and proofs sit above attestation only if proof-system soundness at the deployed parameters is counted with the other cryptographic assumptions and no setup is needed. Every class speaks to what was computed. Whether the verdict gated the answer, and when, needs a mechanism on the serving path that some attestation and logging designs supply and a proof cannot, so an auditor's order differs from the integrity order. The closest attested design attests a wrapper whose classifier runs outside it. We illustrate the systematization with Hallmark, an artifact the author built and ran, which proves with Circle STARKs synthetic threshold-classifier verdicts on a committed prompt of ≤96 bytes and a quantized TinyLlama-1.1B greedy answer, joined by a host check. There, residual trust sits in enrollment and host checks; for exact integer classifiers with public weights, replay needs less trust than the proofs; and the composition accepted classifier proofs made two days after the answer. The proofs spare a verifier the weights and re-execution; timings with unmatched boundaries show nothing about time. No proven security level, hiding, attestation or enforcement is claimed.

**Keywords:** evidence of execution; safety classifiers; trust assumptions; verifiable inference; succinct proofs; remote attestation; transparency logs; AI auditing

## 1 Introduction

Classifiers that screen the inputs and outputs of large language models (LLMs) are a common deployment layer. Llama Guard labels both the user prompt and the model response against a safety taxonomy [D1]. Prompt Guard 2 classifies prompts as benign or malicious, and its smaller variant has 22 million parameters [D6]. Rail frameworks and agent firewalls compose several such checks around one model [D11], [D7], at real cost: enhanced constitutional classifiers report a 23.7% inference overhead relative to the base model [D13]. The EU General-Purpose AI Code of Practice, which addresses providers of general-purpose AI models with systemic risk, lists "monitoring and filtering the model's inputs and/or outputs" as a mitigation (Safety and Security chapter, Measure 5.1) [D24], and signatories must document the implementation and limitations of their mitigations [D24].

The party most affected by a guardrail cannot observe it. Under structured access, users and third parties reach a model only at arm's length, through an API or web interface [D17], and black-box access has been argued to be insufficient for rigorous audits [D18]. This paper asks a narrow version of the verifiable-claims question [D14]: what must a third-party verifier trust to accept that a specified classifier, with a specified threshold, computed a specified verdict on a specified LLM request?

Several kinds of evidence answer parts of that question. A verifier can replay the computation if determinism is engineered [C1], read a tamper-evident log [C18], run a statistical check [C11], rely on refereed delegation [C10], check a hardware attestation report [B2], or verify a proof of inference [A5], [A17]. Two surveys compare some of these by verifiability: Peng et al. rate trusted execution environments and zero-knowledge proofs, among other techniques [A32], and Xia et al. score trusted execution, optimistic and zero-knowledge machine learning [A35]. Neither includes replay or logs, and neither addresses guardrail verdicts. A clearing design for agentic commerce already orders evidence classes partially [F9]; Section 6 states how our order differs. The closest same-question work, Proof-of-Guardrail by Jin et al., uses attestation: an Amazon Web Services (AWS) Nitro enclave runs a guardrail wrapper that calls Llama Guard 3-8B through the OpenRouter API, so the classifier itself runs outside the measured code. The attestation commits to the input and output, a user verifies it in about 5.1 ms, and the trust root is the cloud provider, whose Nitro hypervisor the authors trust to measure the code and protect the enclave's keys [B24].

The title's word "ran" needs care, because it can mean three things. A classifier *computed* a verdict on the request; the verdict *gated* the answer that was served; and it did so *before* the answer was released. All the evidence classes we study speak to the first reading. Only mechanisms that cover the serving path can speak to the other two, and Section 2.2 makes the distinction formal.

This is a systematization paper; the artifact serves as a worked illustration. We make four contributions.

1. **A statement-first account of what "ran" can mean** (Section 2). We separate the computation a classifier performed from whether its verdict gated the served answer and when, and record for every evidence class which of these it can speak to (Table 2).
2. **A systematization of evidence for that statement** (Sections 3 and 4). From a literature base collected by a stated procedure, we assign each evidence class the set of trust elements it needs and compare classes by inclusion of these sets (Table 1, Figure 1). Most of the resulting order is a direct reading of the assignments, and we say which results are. Its use is to make the assignments explicit, and to expose the one edge that is not a reading, proofs over attestation, as conditional on how proof-system soundness and setup are counted. Against the closest prior order [F9], it merges signed records with self-report and makes that edge conditional (Section 6).
3. **Three cross-cutting observations** (Section 4.4): the failure records of every class leave trust in some party or assumption, a claim the sets alone do not establish; request binding is a property of the statement, not of the class; and the integrity order differs from the order an auditor needs for gating and timing.
4. **A worked illustration and a gap analysis** (Sections 5 and 7). Hallmark proves synthetic classifier verdicts and a quantized LLM answer on one request. We use it to show where residual trust sits in one class-5 instance, and name compositions in the literature that could supply each property an auditor-ready receipt would still lack.

> **Box 1. Scope of the claims.** Hallmark's proofs are integrity proofs with public witnesses. They provide no zero-knowledge hiding (`hiding_claim: false`) and no hardware attestation. They do not show that the prompt is what a real user sent, that the served answer depended on the verdict, or when the verdict was computed. No claim is made about whether verification is faster or slower than a native rerun (Section 5.4). The backend is not qualified (`qualified_backend: false`), and no proven security level is stated (Section 5.3). Training is not proved. The three classifiers are synthetic: the frozen multilayer perceptron (MLP) allows every admitted input, and the convolutional neural network (CNN) blocks the benign prompt of the composed demonstration. Hallmark is a research artifact, built and run by the author, not a deployment. Jin et al. state that an attested guardrail "should not be interpreted or advertised as proof-of-safety" [B24], and the same holds here. Evidence that a guardrail ran says nothing about whether its decisions are adequate [E2]. Later sections refer to this box rather than repeating it.

Section 2 fixes the statement and threat model, Section 3 the literature base, and Section 4 the order; Section 5 works through Hallmark, Section 6 reviews related work, Section 7 lists gaps and limitations, and Section 8 concludes.

## 2 Setting and Threat Model

### 2.1 Roles

Three roles recur in every evidence class. The *operator* serves the LLM, runs the guardrail and produces whatever evidence is offered. The *verifier* checks that evidence; it may be the user who sent the request, an auditor, or a regulator acting for the user. The *enroller* fixes, ahead of time, the reference identities against which evidence is compared: classifier, threshold, model and circuit. Among the roles of the Remote ATtestation procedureS (RATS) architecture (Attester, Verifier, Relying Party, Endorser and Reference Value Provider), Endorsers vouch for the Attester's authenticity, Reference Value Providers supply the values evidence is appraised against, and appraisal is a policy decision [B5]. The enroller corresponds to the Reference Value Provider; applying these roles outside attestation is our framing. In Hallmark the caller is both enroller and verifier. Which institution should enroll in practice, and what that choice does to the trust placed in enrollment, is left to future work.

### 2.2 The statement, and what "ran" means

Evidence is always evidence *of* something, so we fix the statement first. Let

> S = "classifier C, with threshold t, produced verdict V on request R, and model M produced answer Y on R".

C and M are identified by their enrolled descriptions (weights, architecture, arithmetic). R is the exact byte or token sequence the classifier and the model consumed. We record six properties for each evidence class. The order of Section 4.1 concerns only the trust behind the first; the others are recorded as separate columns.

- **Integrity.** V is the value that C and t compute on R, and Y is the value that M computes on R.
- **Request binding.** The evidence names R, so a verifier holding R accepts it and a verifier holding any R′ ≠ R rejects it.
- **Hiding.** What the verifier learns about R and about the weights of C and M beyond S itself.
- **Capture provenance.** R is the request the user actually sent, not one chosen by the operator.
- **Adequacy.** C's verdicts implement a useful safety policy.
- **Enforcement and timing.** The served answer Y depended on V, so that a block verdict withholds Y, and V was computed before Y was released.

S is a conjunction of two computations, with no gating clause and no temporal clause. Evidence for S therefore establishes what was computed: the first reading of "ran" in Section 1. A verifier who wants to know that a classifier ran in the sense of screening the served request needs a stronger statement,

> S′ = S ∧ G ∧ T, where G says that Y was released only if V allowed it, and T says that V was computed before Y was released.

G and T concern the serving path, not the two functions. Evidence for S′ must come from a mechanism that observes or controls that path. Section 4 records, for each class, whether it can.

Request binding is defined on the statement, not on the mechanism (Section 4.4). The statement must also say which verdict is meant, since guardrails such as WildGuard return several judgements [D9]. S therefore names the head and the threshold as part of C: an operator that moves t changes verdicts without changing any weight.

S describes an input rail. An output rail computes its verdict on the answer, or on the request and the answer together, V = C(R, Y), and S changes accordingly. Nothing in Sections 2 to 4 depends on which input C reads, except T: an output verdict exists only after Y does, so T must then say that V was computed before Y was released to the user, not before Y was generated. Under streaming release Y leaves the operator piece by piece, and G and T concern every released prefix, which a mechanism on the serving path would have to hold back or check before release. Hallmark does not address streaming, and we leave it outside the systematization (Section 2.4). Two further details are implicit in S. R is the complete input the classifier consumed, including any conversation context and system prompt. And for sampled rather than greedy decoding, S must also bind the randomness from which Y was sampled, committed before generation.

### 2.3 Adversary

The adversary is the operator. It controls the serving infrastructure, chooses which evidence to produce and when, and wants a verifier to accept S when S is false. Its strategies are:

1. **Skip.** Do not run C, and report an allow verdict.
2. **Swap.** Run a different classifier C′ or threshold t′.
3. **Substitute.** Serve the answer of a cheaper model M′. Distribution-level tests detect this behind commercial APIs [C14], and output-only tests need many queries and miss subtle substitutions [C15].
4. **Replay.** Present evidence computed on a different request R′.
5. **Misreport.** Present a verdict V′ that C did not produce on R.
6. **Ignore.** Run C honestly on R, obtain V = block, and serve Y anyway.
7. **Defer.** Serve Y without running C on the live path, and compute C, and any evidence, later and only if a verifier asks.

An evidence class defends against a strategy if, under its trust assumptions, the strategy makes verification fail. The verifier is honest and holds R, because it sent R or because R was disclosed to it. The enroller is honest and completes enrollment before any proof or report is produced. A misconfigured pipeline that silently bypasses a rail leaves the verifier with the same missing evidence as a deliberate skip. The systematization therefore supports detecting missing evidence, not attributing intent. A declared degraded mode, such as a classifier timeout that fails open, is likewise indistinguishable from Skip unless S names an enrolled fallback policy and the evidence records, before release, that the fallback was taken. Ignore and Defer differ from the first five strategies: every computation stays honest, and what breaks is G or T. Evidence for S cannot defend against them; only evidence for S′ can.

### 2.4 Out of scope

Four questions are outside the systematization. *Adequacy*: formal checks find safety holes in all the guardrail classifiers they study [E2], and no evidence of execution repairs that. *Side channels and physical attacks* on the verifier's own machine. *Availability*: an operator can always refuse to serve evidence, and a verifier can only treat missing evidence as failure. *Streaming release*, for the reasons given in Section 2.2.

## 3 How the Literature Base Was Built

The systematization rests on a literature base collected in four strands, one per family of mechanisms: (A) proofs of machine-learning inference and the proof systems beneath them; (B) hardware attestation and confidential computing; (C) replay, determinism, signed and transparency logs, and refereed, optimistic and statistical verification; and (D) the guardrail landscape, assurance literature and governance texts. Each strand was searched on 2026-10-30 with public topic terms in web search and on primary pages (arXiv, the Cryptology ePrint Archive of the International Association for Cryptologic Research (IACR), venue proceedings, standards bodies, official repositories), with follow-up searches for same-question work and, during revision, for sources reviewers named. A source was included if it describes a mechanism that produces evidence about the integrity of an inference or a record of it, reports a failure of such a mechanism, or states a governance demand for such evidence. Every source was opened on a primary page or metadata endpoint, and its annotation records trust root, request binding, hiding, verifier cost and failure mode as the source states them.

Reading depth varies, and we report it. Before review, an integrity check of this manuscript re-read the cited passages from source full texts for 69 of the 81 references then cited. Among the sources used to place a system in a class, the following were checked at abstract or title level only: the prompt binding of DeepProve [A17], ZKML [A8], Sigstore [C20], and the audit-framing works [D16], [D18]. Proof-of-Guardrail [B24] was read in full during revision, which changed its description (Section 4.3). Sources added in the final revision at reviewers' request ([A39]–[A42], [B25], [B26]) were checked on their primary pages for the specific statements cited; Seal-then-sample [A22] was re-read for its setup. Class assignments of systems we did not run come from their own descriptions and may err in either direction.

## 4 Evidence Classes Ordered by Trust

### 4.1 Trust universe and order

Peng et al. rate the verification capability of trusted execution environments (TEEs) as "Limited (attestation)" and of zero-knowledge proofs as "Strong" [A32]; Xia et al. score verifiability as 5 for zero-knowledge machine learning (zkML), 3 for optimistic machine learning (opML) and 2 for TEEs, and count trusted parties: "zkML requires 0 trusted parties (only mathematical assumptions)", opML at least one honest challenger and TEEs the hardware manufacturer [A35]. We turn their scalar axes into a relation over a set U of trust elements on which evidence for the integrity of S can rest:

- *O*, the operator's honesty;
- *E*, correct enrollment of reference identities [B5];
- *P*, a correct implementation of C and M, whether in the verifier's code, a delegated program, a measured image or a circuit [A23], [A30];
- *K*, cryptographic assumptions (hashes, signatures, commitments and proof-system soundness) at the deployed parameters [A24], [A28];
- *N*, an honest participant in the ceremony that generated a structured reference string, for proof systems that need one [A41], [A42];
- *D*, deterministic execution [C1], [C10];
- *H*, one honest replica or challenger, online when needed [C6], [C9];
- *T*, empirical soundness of a tolerance or sampling check, including the unpredictability of what is sampled and, for secret-based checks, the secrecy of the verifier's secret [C11], [C12], [C13];
- *W*, the attestation root: the hardware, firmware and keys of whoever signs the attestation. W has three instances. For CPU TEEs it is a silicon vendor (*W*_v) [B2]. GPU TEEs add NVIDIA's keys (*W*_g) to the CPU vendor's, since H100 confidential computing relies on a CPU TEE [B6], so their set is strictly larger and they sit below CPU TEEs in the order. For AWS Nitro Enclaves it is the cloud provider's hypervisor and keys (*W*_c) [B24].

Each class X has a trust set τ(X) ⊆ U (Table 1). Define X ⪯ Y, read "Y needs no more trust than X", to hold if and only if τ(Y) ⊆ τ(X). Inclusion is reflexive and transitive, so ⪯ is a preorder. It is not antisymmetric on classes, because self-report and signed records receive the same set. Its quotient, which merges classes with equal trust sets, is a partial order; we call the preorder *the order*, and Figure 1 draws its quotient. Two modelling choices fix the bottom and the shared elements. Because O is the adversary, evidence whose integrity relies on O is no evidence against it, so we assign such a class the whole universe, τ = U, a convention that places operator-reliant classes at the bottom by construction. And E is assumed for every class, P for every class that checks a computation. The order compares classes; Result 5 below refines it by the computation and by what the verifier holds, and is not a relation between classes.

### 4.2 What the order says

The order has four unconditional results and a refinement. Results 1 to 4 are readouts of Table 1, not discoveries: E and P are shared by convention, the bottom is placed by convention, and each class above the bottom other than proofs carries at least one element proofs lack (D, T, H or W), so incomparability follows from the assignments. We state them because the assignments carry the content, and a reader who disputes one can see which result changes.

1. Self-report (0a) and signed or logged records (2) rely on O and form the bottom class. Black-box testing (0b) binds no request and is not compared.
2. Replay (1), with τ = {E, P, D}, needs no more trust than refereed delegation (3b), with τ = {E, P, K, D, H}. Replay spares the verifier K and an honest party, at the price of a rerun.
3. Statistical checks (3a), refereed delegation (3b) and attestation (4) are pairwise incomparable. A verifier who distrusts the attestation root prefers 3b to 4; one who cannot ensure an honest challenger is online prefers 4 to 3b.
4. Replay and proofs (5), with τ = {E, P, K}, are incomparable in general: one needs D, the other K.
5. *A refinement, not a class relation.* When the computation is an exact integer program and the verifier holds the weights, D holds by construction. Replay of that computation then needs only {E, P}, less than every other class, proofs included. Section 5.4 meets this case.

Of the 21 pairs among the seven compared classes, 15 are comparable with the dashed edges of Figure 1 and 12 without them; all but four comparable pairs (one without the dashed edges) involve the bottom class. Among the five classes above the bottom, 6 of the 10 pairs are incomparable with the dashed edges and 9 without.

The three edges from 3a, 3b and 4 into 5 are conditional: they hold only because K places proof-system soundness at the deployed parameters in one class with the hash, signature and commitment assumptions the other classes already need. A verifier who separates the two finds 5 incomparable with 3a, 3b and 4, directly above the bottom class, and that separation is reasonable whenever the parameters carry no proven security level, as for Hallmark (Section 5.3). Proof systems whose polynomial commitments need a structured reference string, such as KZG commitments [A41], also need N, and for them the three edges fail even when soundness is counted within K. The order thus supports no claim that proofs dominate attestation: proofs replace W with proof-system soundness, and possibly N, and whether that is an improvement depends on parameters and setup the order does not weigh. Figure 1 draws both readings with equal weight.

Class numbers are labels, not heights, and the order is not a ladder: replay (class 1) needs less trust than refereed delegation (class 3b). Like the graded levels of the Supply-chain Levels for Software Artifacts (SLSA) specification [C23], the order is a vocabulary for stating what evidence rests on, not a recommendation. Hybrids are compositions, not new classes: Slalom pairs a TEE with Freivalds checks [B11], Atlas a TEE with transparency logs [C24], and Seal-then-sample [A22] and IMMACULATE [C13] pair proofs with sampled coverage (5 + 3a).

### 4.3 The classes

**Class 0: self-report (0a) and black-box testing (0b).** A model card or safeguard report is written by the developer about its own system [C25], [D23]; the verifier trusts the author, and nothing binds the document to a request. A two-sample test can tell from output distributions whether an API serves a reference model, with a median power of 77.4% at an average of 10 samples per prompt [C14], but it binds no request and can be evaded by routing audit traffic differently [C15], so it is an external check on self-report, outside the order.

**Class 1: replay.** The verifier re-executes the classifier or model on R and compares results. For floating-point LLM serving this works only when determinism is engineered: with batch-invariant kernels, 1,000 completions were identical, against 80 distinct completions by default [C1]; otherwise outputs vary with batch size, GPU count and GPU type [C2] and across runs of hosted APIs [C3]. The verifier must hold the enrolled weights and match the operator's configuration [C1], [C4]. We infer that replay binds only the input the verifier replays, not the request the operator served.

**Class 2: signed or transparency-logged records.** A signed, append-only record shows that a key holder wrote an entry and did not later alter or fork it, not that the logged event was computed correctly [C16], [C18]. For a guardrail record the writer is the operator, and permanence also rests on auditors that compare views [C17]; with keyless signing, the signer's identity also rests on the OpenID Connect identity provider [C20]. A log binds the claim, not the computation [C17], but it can add time: an entry written before the answer is released fixes the claimed verdict at that moment.

**Class 3a: statistical or sampled checks.** The operator commits to intermediate signals, which the verifier checks against the claimed model and prompt within a tolerance. TOPLOC, a locality-sensitive hashing scheme, reports no false positives or negatives in its authors' tests, at 258 bytes per 32 new tokens for Llama 3.1-8B-Instruct, with empirical rather than cryptographic soundness [C11]; SVIP is secret-based: it uses a learned identifier with non-zero error rates and a secret that the provider must not learn [C12]. IMMACULATE audits a sampled fraction of requests using verifiable computation, so unaudited requests carry no proof [C13]; like Seal-then-sample, it composes class 5 with sampling.

**Class 3b: refereed or optimistic delegation.** The result is correct if at least one server or challenger is honest [C6], [C10]; optimistic schemes also need that party online within a challenge window [C8], [C9]. Binding to the delegated program and input is native, the happy path is cheap, and a dispute narrows to a single step [C9]. All schemes in this class depend on deterministic execution and fail if every party colludes [C9], [C10].

**Class 4: hardware attestation.** A report signed with keys of the attestation root shows that a genuine platform launched a measured image, which placed chosen data in the report [B2], [B5]. Appraisal against reference values [B5] is, in our reading, not a proof of correct computation. For CPU TEEs the verifier trusts the silicon vendor, its firmware and key chain (W_v) [B3]; for GPUs, NVIDIA's keys together with a CPU TEE on which H100 confidential computing "relies" [B6], so a GPU TEE needs both roots. Vendor roots have failed in practice. Foreshadow forged Intel Software Guard Extensions (SGX) attestation [B13], the ÆPIC Leak attack extracted SGX attestation keys "within a few seconds" [B14], CacheWarp broke the integrity of AMD Secure Encrypted Virtualization with Secure Nested Paging (SEV-SNP) [B15], and TEE.fail forged Intel Trust Domain Extensions (TDX) quotes that pass Intel's quote verification at the UpToDate level and let attackers "borrow" GPU attestation reports across the CPU–GPU boundary [B16]. For AWS Nitro Enclaves the root is different: the cloud provider's Nitro hypervisor measures the code and protects the enclave's keys, so the verifier trusts AWS (W_c) [B24]. None of these attacks targets that root, and none of the sources we hold evaluates attacks on Nitro; in our reading, resistance to physical access there rests on the provider's operational controls, which we cannot assess. We note, as our own inference, that in a Nitro deployment the party that holds the attestation keys may also host the operator, a trust concern of a different kind from a vendor break.

Request binding through the report-data field is a choice of the measured program [B2]: Attestable Audits binds model hash, prompt and response [B23], and Proof-of-Guardrail commits to input and output, with one variant omitting the input [B24]. What the measurement covers matters as much. In Proof-of-Guardrail it covers the guardrail wrapper, while Llama Guard 3-8B is called through the OpenRouter API and the agent's model through an external API [B24]. The integrity of V therefore rests on the API operator, outside the attested boundary. On our universe that is operator-reliant evidence for V, so the attestation speaks at class 4 to the wrapper (which request it handled, what it received and what it released), not to the computation of V. Folding the third-party classifier API into O is a modelling choice: U has no element for a third party outside the measured boundary, and assigning τ = U is the conservative reading. If the API operator is instead treated as a separate trusted party, U gains an element for its honesty, and the evidence for V rests on {E, P, K, W} plus that element: a strictly larger set than class 4's, so it sits below class 4 and above the bottom class rather than at the bottom. Either way the attestation covers the wrapper, not the classifier's computation. Because the measured code handles the verdict, attestation can also cover gating and timing, if that code withholds the answer on a block verdict and reports at serve time. Hiding from the host holds within the stated threat model [B3]. Verification is a signature and certificate check, about 5.1 ms in Proof-of-Guardrail; reported overheads, from unmatched settings, are below 7% for most LLM queries on Hopper GPUs [B8] and +29.7% latency for Proof-of-Guardrail's Llama Guard 3 step on one m5.xlarge instance [B24].

**Class 5: proofs of execution.** A proof shows that a committed or public function computed the output on a committed or declared input, under cryptographic assumptions [A7], [A32]. Scalable transparent arguments of knowledge (STARKs) need no trusted setup [A24]. Systems whose polynomial commitments use a structured reference string, such as KZG [A41], need a setup ceremony, for which multi-party protocols exist [A42], and so need N. Seal-then-sample uses HyperKZG over BN254, with locally generated test parameters in its measurements [A22]. The S-two documentation describes its Circle STARKs as conjectured to be sound under two assumptions: that the hash function resists collisions in the random-oracle model, and that the small-distance decoding problem implicit in Fast Reed–Solomon Interactive Oracle Proofs of Proximity (FRI) is hard [A28]. Binding holds in input-bound designs [A5], [A12], [A17], [A22] and is not stated for some LLM provers [A15]. Published designs report verification in milliseconds to seconds, for example 59.3 ms for VGG16 [A5], and FRI has a strictly logarithmic verifier [A25]; Section 5.4 records Hallmark's figures without comparing them to a rerun.

Class 5 has its own failure record, at three levels. At the statement level, "ghost weights" keep the declared architecture, collapse the computation and still pass the circuit, because a proof attests only the committed function [A23]. At the circuit level, a systematization of 141 vulnerabilities in implementations of succinct non-interactive arguments (SNARKs) finds most of them in circuits, with under-constrained bugs the most common class [F1]. At the proof-system level, weak Fiat–Shamir transformations were found in 36 implementations affecting 12 proof systems, and knowledge-soundness attacks were demonstrated for four of them [F2]. Formal verification narrows the second risk only where it reaches: a Lean proof covers the Cairo arithmetic intermediate representation (AIR) used by StarkWare's S-two prover and no other AIR [A30]. ### 4.4 Three observations across classes

**Every class's failure record leaves trust somewhere.** This claim comes from the failure records, not from the sets. Under inclusion, transparent proofs add no element to the E, P and K that every class above the bottom needs, and replay of an exact integer program needs only E and P. What the sets cannot show is how much each element holds. The K of proofs includes proof-system soundness at the chosen parameters [A28] and their P includes circuits that have failed in practice [F1]. Attacks show where the residual trust goes: to physical security and keys at class 4 [B16], and to what is committed and how it is constrained at class 5 [A23], [F2]. In each case the evidence is sound for its stated relation, and the failure lies in an assumption outside it. This is also our answer to the count of "0 trusted parties" for zkML [A35]: a count of parties leaves out enrollment, implementation and parameters, which is where the recorded failures of proofs lie.

**Request binding is a property of the statement, not of the class.** Replay binds what the verifier replays and, we infer, cannot speak for the served request. Attestation binds only if the measured program writes the request hash into the report [B2], which Proof-of-Guardrail makes optional [B24] and which breaks when GPU reports are not bound to a specific CPU enclave [B16]. Proofs bind only if the request, or a commitment to it, is among the public inputs [A12], [A32]. Two systems in one class can therefore differ in whether they answer S at all, so a verifier must read the statement, not the class label.

**The integrity order and the auditor's order differ.** Table 2 reverses much of Figure 1. Proofs need the least trust for integrity when soundness is counted within K, but say nothing about G or T, while attestation and pre-release logs sit lower for integrity yet can observe the serving path. An auditor asking whether the safeguard was in effect for this request should read Table 2 first; reaching S′ needs a composition (Section 7).

## 5 Case Study: Hallmark

Hallmark is a public research artifact, built and run by the author (Section 7.2), that proves a classifier verdict and an LLM answer and joins them on one request. We use it as a worked illustration of the systematization, not as a system contribution or a test: once its relations are fixed, what it shows follows from the definitions of Section 4, and its value is to show concretely where residual trust sits in one class-5 instance. Its statements come from the frozen records listed under Data and Artifact Availability, and design details from `docs/PROOFS.md`, `docs/CIRCLE-CLASSIFIERS.md`, `docs/LLM-PROOF.md` and `README.md` at commit `adddf9a`.

### 5.1 The relations

**Classifier relation.** For a fixed integer classifier F and threshold t compiled into the circuit, and a complete prompt x of at most 96 bytes of UTF-8 (8-bit Unicode Transformation Format) text, a proof shows that the verdict equals 1 (pass) exactly when F(x) < t, and that x matches a salted SHA-256 commitment; each proof carries 100 public fields. Three synthetic classifiers instantiate F: a rule that blocks inputs containing the bytes `BAD`; a four-hidden-unit integer MLP over the 256 byte counts, with threshold 0; and a contextual byte CNN with width-24 causal windows over 32 channels and a masked maximum, with threshold −3733 (`docs/CIRCLE-CLASSIFIERS.md`). The circuit constrains the complete input (96 bounded byte slots with a prefix mask, an exact byte count and zero padding), so a prover cannot classify a prefix and commit to a longer prompt, and signed accumulators use bounded limb decompositions with constrained carries so that no integer alias modulo the Mersenne-31 prime passes. Proofs are produced by the S-two Circle STARK prover (repository `stwo`) over the Mersenne-31 field [A27], [A28], through a gate-level AIR with fixed, caller-enrolled wiring. A valid proof can certify a block verdict: proof validity and classifier approval are separate outcomes.

**LLM relation.** The LLM proof concerns a quantized TinyLlama-1.1B under the disclosed integer profile `y-attnout-w12`. The prompt "Name the capital of France in one short sentence." becomes 25 tokens under the pinned chat template. One causal block of 32 positions holds those tokens and the first seven answer tokens, and the output head's argmax at positions 24 to 31 yields eight answer tokens ending in the end-of-sequence token: "The capital of France is Paris." (`docs/LLM-PROOF.md#the-statement`). The proof covers the embedding, all 22 transformer layers, the final normalisation and the output argmax. The LLM prover is zk-inference-prover from the Singapore AI Safety Hub (hereafter the SASH prover), an open-source STARK prover for a quantized transformer, used at a pinned commit [SASH]. The proved relation is the quantized profile, not every floating-point execution of TinyLlama.

**Composed relation.** Let σ₁, …, σ₂₃ be the segment statements (22 transformer segments and one final-normalisation and argmax head, which together cover the embedding, all 22 layers, the final normalisation and the argmax), ρ₁, …, ρ₂₂ the residual links (each segment's output commitment equals the next segment's input commitment), λ₁, …, λ₇ the token links (each output token is the next input token), κ the statement of each enrolled classifier, and β the host predicate that the classifier's opened prompt and the LLM's prompt tokens are the same request. The evidence for S is

> (∧ σᵢ) ∧ (∧ ρⱼ) ∧ (∧ λₖ) ∧ (∧ κ) ∧ β, over identities enrolled beforehand.

If every σᵢ and κ holds by proof and every ρⱼ, λₖ and β holds by the caller's check, S holds for the enrolled C, t and M on R. The σᵢ and κ rest on K. The links are checked by the SASH verifier and a caller-side guard, and β by host code, so all three belong to P. The evidence is a linked bundle, not a recursive proof, and it is verified only by the SASH prover's own pinned implementation; a bug shared by prover and verifier would go undetected, which we count as residual P. Lim and Yong describe a system that also proves TinyLlama-1.1B with prompt and answer binding [A22]. We did not establish whether it is related to the SASH prover and assert no relation either way (Section 7.2). The full-coverage greedy-answer bundle is a capability of the SASH prover as Hallmark uses it. Hallmark contributes the classifier relations, the enrollment and the host join.

### 5.2 Enrollment, binding and what the caller checks

A prover cannot authenticate its own parameters, so the caller enrolls them before any proof exists. For each classifier it enrolls the compiled program hash, wiring, constants and the S-two preprocessing root; for the LLM it enrolls the model, shape and calibration roots and the exact token case. After proving, the caller (1) rebuilds the expected public inputs, context digest and classifier identity from its own copy of the request; (2) requires exactly one proof for each enrolled classifier; (3) runs each verifier in a fresh process that receives only the enrollment, the public inputs and the proof; (4) checks that both relations refer to the same opened request; and (5) combines the verified verdicts with `all-pass`. It also applies the pinned tokenizer and chat template and checks that the eighth answer token is the end-of-sequence token. Inside each relation binding is cryptographic; across them it is the host check β. If enrollment followed proving, an operator could choose a model or circuit that gives the answer it wants and present it as the reference, so the expected roots must come from the caller's own enrollment. The formula is the one the S-two library itself computes. In version 2.2.0, the exact version Hallmark pins, `PcsConfig::security_bits` returns the proof-of-work bits plus `FriConfig::security_bits`, and the latter returns the log blowup factor times the number of queries (`stwo-2.2.0/src/core/pcs/mod.rs`, lines 44–46; `src/core/fri.rs`, lines 77–79) [A28]. The same query-and-grinding form is the first of three values whose minimum StarkWare's earlier ethSTARK prover reports as its "conjectured security", and that prover's documentation points separately to a proven bound on FRI soundness [A39], [A40]. For the classifiers the formula gives 16 + 4 × 80 = 336, a query-and-grinding conjecture that the unanalysed extension-field and hash terms below cap, not a proven bound. Applied to each LLM segment's parameters it gives 0 + 1 × 100 = 100, which matches the 100 conjectured bits that the SASH prover reports for its configuration [SASH]; the Hallmark repository records that this is not an independent security qualification.

Three qualifications apply. First, the formula counts only query and grinding terms and rests on the conjectures of Section 4.3; it is not a proven bound. For orientation only, counting the query term of the proven analyses (plus the classifiers' 16 proof-of-work bits), the unique-decoding regime gives about 41.5 bits per LLM segment (100 × −log₂ 0.75, at rate 1/2) and about 89 for the classifiers (16 + 80 × −log₂ 0.53125, at rate 1/16), and the regime up to the Johnson bound [A40] gives at most about 50 and 176. These approximations are our own; they ignore the commit-phase and field-size terms, which can only lower them, and they are not a provable bound for either configuration. Second, every figure above ignores other limits, among them the secure extension field QM31 (degree 4 over Mersenne-31, about 2^124 elements) and the hash's collision resistance, which cap both configurations, so the classifier configuration reaches less than the conjectured 336. Third, the LLM evidence composes 23 proofs. By a union bound, the bundle's conjectured soundness error is at most 23 times the per-proof error, which loses at most log₂ 23 ≈ 4.52 bits, about 95.5 conjectured bits for the bundle. This is our own derivation, not a statement of any source. Formal verification of an S-two AIR does not extend to Hallmark's classifier or LLM AIRs [A30]. Hallmark's class-5 placement is therefore that of a class-5 relation at unqualified parameters, and the dashed edges of Figure 1 do not hold for it.

### 5.4 What the case illustrates

We read the recorded experiments against four points. Three follow from the definitions of Section 4 once Hallmark's relations are fixed, so the case shows them concretely rather than testing them; the third concerns cost, which only matched measurement could settle.

**Residual trust sits in enrollment and host reconstruction.** *Skip* fails if the verifier requires the complete roster of proofs before it accepts the answer; a verifier that asks for proofs only later turns Skip into Defer. *Swap* fails because classifier identity, program hash and threshold are fixed by enrollment. *Substitute* fails at the enrolled model, shape and calibration roots. *Replay* fails because the input commitment and context digest are public inputs the caller recomputes (Section 5.2). *Misreport* fails because the circuit constrains the public verdict to the threshold decision. Each defence holds only under the caller's enrollment and reconstruction, which are E and P. None addresses capture provenance: if the operator chooses R, every proof can be valid for a request the user never sent.

**For exact integer relations with public weights, replay needs less trust than a proof.** The classifier weights and witnesses are public, and the demonstration's caller already reruns native inference to derive the expected verdicts; replay of an exact integer program needs only {E, P}, while the proof needs {E, P, K} at unqualified parameters. In the demonstrated configuration the classifier proofs therefore add no integrity evidence for this caller. The same holds for a verifier that holds the TinyLlama weights, since a rerun under the proved relation reproduced the proved answer (exp-R1-native-rerun). The proofs become non-redundant only for a verifier that lacks the weights or will not re-execute; a deployment with private weights would also need hiding, which Hallmark lacks (Box 1).

**Proofs remove the verifier's need for weights and re-execution; the timings settle nothing about time.** The proofs let a verifier check the answer without the TinyLlama checkpoint (about 2.2 GB) and without executing any model, at the price of obtaining a 737,858,641-byte bundle. Whether this is also faster than a rerun is not settled by the records, and we make no claim either way. The recorded figures (Table 4) are 3.40–3.53 s to verify the 23-proof LLM bundle, against medians of 0.769 s for one quantized greedy answer under the proved relation and 0.235 s for an fp32 reference answer; and 0.807 s for nine proof-only classifier verifier processes, against about 0.61 s for the nine native executions. They support no direction, for three reasons. The boundaries differ: verification timers include process start and proof loading, while the LLM rerun timers exclude model loading, calibration and tokenization. The classifier verification total rests on one cold first process, 0.345 s of 0.807 s against 0.050–0.079 s for each of the other eight; with that process at a sibling's value the total would be about 0.51–0.54 s, so the sum is set by one cold start. And the CNN rerun, about 0.2 s per request and nearly all of the 0.61 s, times Hallmark's pure-Python reference interpreter, whose timed call also hashes the weights and tokenizer, validates the input profile and decodes the program constants before it evaluates the integer graph; it measures that implementation, not the integer program. A comparison would need warm, repeated verifier runs, a compiled rerun with loading and hashing outside the timer, and matched boundaries for the LLM; none was run. Hallmark instantiates the trust set of class 5, not a cost profile.

**Evidence for S cannot show gating or timing.** The artifact exhibits both gaps. The CNN's verified verdict on the France prompt is block, a verified proof of an answer to that prompt exists, and the composed result reports that the request does not pass. Nothing in the evidence shows whether that answer was withheld. The three classifier proofs were produced on 2026-10-28, two days after the answer proofs they were joined with, and the caller accepted the join (exp-L1-llm-proving, exp-J1-composition). For this statement, proving after the fact cannot be told apart from proving in line.

## 6 Related Work

**Proofs of ML inference.** Verifiable neural-network inference began with interactive proofs for small networks [A1] and moved to SNARKs for CNNs [A5] and ImageNet-scale models [A7], with compilers that co-design quantization and proving [A4] or optimize circuit layout [A8], or compile models to basic blocks [A13]. LLM provers cover full 13B inference [A15], all generated tokens of GPT-2 and Gemma 3 [A17], agent transcripts with tool outputs [A19], and sampled layerwise coverage up to 70B with prompt and answer binding [A22]. Jolt Atlas applies lookup arguments to Open Neural Network Exchange graphs [A14], and ML has been compiled to S-two before [A29]. Hallmark contributes no proof system.

**Attestation-based inference and audits.** Benchmarks of confidential computing report moderate overhead for LLM inference on CPU and GPU TEEs [B8], [B10]. Cai et al. propose TEEs as a practical remedy for model substitution in APIs [C15]. Attestable Audits runs safety benchmarks in Nitro enclaves and binds prompt and response in an interaction attestation [B23]. Proof-of-Guardrail asks our question and answers it with an attested wrapper whose classifier call leaves the measured boundary (Section 4.3) [B24]. Deployed services already compose attestation with transparency: in Apple's Private Cloud Compute, user devices send data only to nodes that cryptographically attest to running publicly listed software, and the log and binary images are made publicly available for inspection [B26], a class-4 and class-2 composition at production scale, built for privacy rather than for guardrail verdicts. Cove composes TEE-attested computations into multi-party audit workflows, including attested inference [B25].

**Safety and fairness claims with proofs.** South et al. produce zkSNARK attestations that a private-weight model meets aggregate accuracy, bias or safety metrics on a dataset [A9]. ZkAudit proves that published commitments to data and weights derive from training [D19]. FairProof issues a fairness certificate specific to each user query, under a model kept confidential through commitments and zero-knowledge proofs [F3]. It is precedent for per-input proofs of a safety-relevant property, though not of a guardrail verdict. A vendor blog describes wrapping an automated-reasoning guardrail pipeline in zkML so that "every action carries cryptographic proof of execution", without a binding mechanism or a published evaluation [E1].

**Replay, delegation and logs.** Refereed delegation goes back to protocols in which several servers compute and a referee resolves disagreement cheaply [C6], [C7]; Arbitrum [C8], opML [C9] and Verde [C10] carried challenge-and-bisect to smart contracts and ML. Zhou binds agent tool use with signatures and shows that replay-based verification yields only a probabilistic bound [A38]. Keyless signing gives identity-bound records [C20], and model signing applies it to weights [C22].

**Accountability and audit.** Kroll et al. argue that automated decisions can be made accountable by assuring procedural regularity, meaning that decisions follow an announced set of rules, verifiable without revealing key attributes of the decisions [F5]. Enrollment before proving is a concrete instance of rules announced in advance. Internal audit frameworks address the accountability gap through documented internal process [D15]; the evidence systematized here is instead checkable from outside the organisation, request by request. It sits at the application layer of a layered audit [D16], where it adds evidence that black-box access cannot provide [D18] without replacing governance or model audits.

**Orderings of evidence.** Peng et al. and Xia et al. order evidence classes by verifiability [A32], [A35]. RAILS, a clearing design for agentic commerce, orders its admissibility classes as SELF ⪯ SIGN ⪯ {WIT, REC} ⪯ ATT ⪯ PROOF and states that they "form a partial order, not a scalar ranking" [F9]. On the classes both cover, the two orders differ in two places. RAILS places signed records above self-report; for the integrity of a verdict ours merges them, because a signature by the operator authenticates the record, not the computation (Section 4.3). And RAILS places proofs above attestation without qualification, whereas ours makes that edge conditional on counting proof-system soundness at the deployed parameters within K, and drops it for proofs that need a setup ceremony. RAILS has no replay, statistical or refereed classes, and its relations are asserted class by class; ours are readings of explicit trust sets, so a reader can see which assignment each edge depends on, and ours also records request binding, capture provenance, gating and timing per class. Rizzini et al. systematize integrity claims in privacy-preserving federated learning, binding each claim to a round identifier against replay, but do not order mechanisms [F7]. Formal verification of guardrail classifiers addresses adequacy, the axis our order leaves out [E2].

**Search outcome and novelty.** The earlier version of this paper bounded its novelty statement by three works screened at abstract level; we have now read them. Balan et al. propose cryptographic verifiability for an AI pipeline from data to inference and unlearning; they prove inference on a given input, but bind no request, treat no guardrail and compare only TEEs with proofs [F6]. Rizzini et al. [F7] concern federated learning, not LLMs or guardrails. Keršič et al. survey and compare on-chain zkML frameworks [F8]; we could read only the abstract, which does not concern guardrails. The guardrail companion work named in the Jolt Atlas paper, which claims zkML for "succinctly verifiable agentic guardrails" [A14], was searched for on arXiv, the IACR archive and the authors' site, and not located. That site lists a forthcoming work, with a preprint available on request, on verifiable receipts that a policy check was enforced on an agent action [F10]; we have not read it. With the vendor blog [E1], these are the closest same-question works on the proof side; they concern automated-reasoning policy checks, not classifiers. To our knowledge, based on the searches described in Section 3 and completed on 2026-10-30, no peer-reviewed or preprint work reports succinct per-request proofs of a guardrail-classifier verdict composed with an LLM-answer proof. The statement is narrow: each element of the case has precedent (Sections 4 and 6), the classifiers are synthetic and the composition is a host join. The case matters here for what it shows about the order, not for priority.

## 7 Toward an Auditor-Ready Receipt, and Limitations

### 7.1 Gaps

A receipt a deployer could hand to an auditor would need more than any single class provides. We list the gaps by the property each concerns, with the compositions in the literature that could supply it. None is estimated here.

1. **Gating and timing (S′).** Evidence for S is consistent with an operator that ignores a block verdict or proves after serving (Section 5.4). Two compositions could reach S′. An attested wrapper that withholds the answer on a block verdict and reports at serve time covers G and T [B5], [B24]; composed with a proof whose public input is the wrapper's request commitment, it would also move the verdict computation inside a proved relation. A logged record of the proofs' public inputs, written before the answer is released, would fix the claimed verdict in time for later proofs to match [C16], [C18], though it would not show that the classifier ran in line. Deployed attested services [B26] and attested audit workflows [B25] show that the attestation half can be built at scale; in our sources neither reports gating on a classifier verdict. Neither composition is shown here.
2. **Capture provenance.** The proofs bind a committed prompt, not the prompt a user sent. DECO lets a user prove that data accessed over TLS came from a particular website, without trusted hardware or server-side changes [F4], which makes it a primary route for authenticated capture; zkAgent applies such sub-proofs to agent transcripts [A19]. Interaction attestations [B23] and pre-committed per-request logs [C13] are alternatives, and an attested capture service could write the request commitment into its report data [B2].
3. **Hiding.** With public witnesses, a deployer cannot hand auditors prompts containing user data without a separate privacy basis. Weight privacy is costly in other stacks (Mystique reports 28 min for ResNet-101 with a committed private model against 5 min with a public one [A6]), and no source we hold measures it on a Circle STARK stack. Public witnesses let the auditor read the committed classifier, which blunts the hidden-weight attack [A23]; a hiding variant would need another way to give that assurance.
4. **A verifier cheaper than a rerun.** The recorded case does not establish one (Section 5.4). Proving is a separate cost: the 1.1B answer took about 54 s of proving sessions on one H200 (Table 4), so proving in line, before release, would add on the order of a minute per request for this model on that hardware.
5. **Enrollment governance.** The case moves residual trust to enrollment (Section 5.4), and no class supplies it. Someone must fix the reference classifiers, thresholds, model roots and fallback policies, and evidence when each was fixed or changed, before the requests it governs. In RATS terms this is the Reference Value Provider's role [B5]; model signing [C22] and transparency logs [C18] could record enrollment and threshold changes before use. Who should enroll (the deployer, an auditor or a regulator) is left open; the choice decides whom E asks the verifier to trust.
6. **Real guardrails.** The smallest real guardrail classifier in our sources, Prompt Guard 2, has 22 million parameters and a 512-token context [D6], and open guardrails reach a 12-billion-parameter multimodal classifier [D4]; no source we hold proves one at class 5. Since the proved LLM relation has 1.1 billion parameters, size alone does not rule out the former, but its context, architecture and integer-export fidelity would have to be shown.
7. **Qualification.** A provable soundness bound for both configurations, an independent LLM verifier, formal verification of the gate-level AIRs [A30], and witness-level testing of the gadgets against the circuit-failure classes of Section 4.3 [F1] are all missing.
8. **A compact receipt.** The LLM evidence is a 737,858,641-byte linked bundle per request and the join is host code. Under the AI Act, providers of high-risk AI systems must keep the logs their systems automatically generate, to the extent the logs are under their control, for a period appropriate to the system's intended purpose and of at least six months unless Union or national law provides otherwise (Art. 19(1)) [C26], and deployers have the same duty (Art. 26(6)) [C26]. We do not argue that a guardrailed chat service is high-risk, and the Act, as read, does not ask that logs be proofs, so we claim no retention cost; retaining one bundle of this size per request would simply scale with request volume. A deployer need not prove every request: committing every request's public inputs to a log before release, and proving or verifying only a sample or on challenge, is the pattern IMMACULATE uses [C13]. It also constrains Defer, since an operator that commits to a verdict before computing it is caught whenever a sampled proof disagrees.
9. **Multi-rail and output pipelines.** Guardrail frameworks orchestrate several rails [D7], [D11]; Hallmark proves individual input classifiers combined with `all-pass`. No source we hold treats proofs over rail orchestration logic, output rails under streaming release (Section 2.2) or fail-open fallbacks (Section 2.3).
10. **Record keeping over time.** The AI Act requires high-risk AI systems to allow automatic recording of events (Art. 12(1)) [C26], and the Code of Practice asks providers of general-purpose AI models with systemic risk to implement and document mitigations such as input and output filtering (Measure 5.1) [D24]. Neither text, as read, mandates cryptographic per-request evidence, so the systematization offers possible forms of evidence rather than meeting a stated demand; we read the Regulation as published in the Official Journal of 12 July 2024 and have not verified whether later amendments change these articles. Transparency logs are a deployed template for such records [C18], and Hallmark records none.

### 7.2 Limitations

The study has six limitations. First, the case is one instance: one prompt, one model profile and classifier inputs of at most 96 bytes, so what it shows is illustration, not a test or a measurement of generality. Second, the experiments were run by the author, who also built the artifact, and the trust universe was drawn with the results known; Section 4.2 states which edges depend on its granularity. Third, reading depth varies across sources (Section 3). Fourth, the validation mutations are engineered test cases, not an adversarial evaluation: there is no witness-level fuzzing and no completeness argument for the gadgets (Appendix A), and the LLM verifier is the prover's own implementation (Section 5.1). Fifth, the code, the research record and this manuscript were produced with AI assistance (back matter). Sixth, two questions are left open: runtime root derivation was not timed separately from LLM verification (Section 5.5), and the relation, if any, between Seal-then-sample [A22] and the SASH prover was not established, so we assert none (Section 5.1). The order also concerns one statement, S. A different statement, such as model-level safety metrics [A9] or training provenance [D19], may order the same mechanisms differently.

## 8 Conclusion

Evidence that a safety classifier ran on a request is not one thing. Each class establishes something different and asks the verifier to trust something different. Written as trust sets, most classes above the operator-reliant bottom cannot be ranked, and proofs sit above attestation only if proof soundness at the deployed parameters is folded into the cryptographic assumptions other classes need, and only for proofs without a setup ceremony. Every class speaks to what was computed. Gating and timing, the senses of "ran" an auditor often cares about most, need a mechanism on the serving path, which some attestation and logging designs can provide and a proof of S cannot. In the Hallmark case, residual trust sits in the caller's enrollment and host checks; for its exact integer classifiers with public weights, replay needs less trust than the proofs; its proofs spare the verifier the weights and the re-execution; and its own composition accepted proofs made two days after the answer. The next steps are compositions that reach S′ (an attested, gating wrapper or a pre-release log composed with proofs), authenticated capture, governed enrollment, a provable soundness bound, and a proof of a real guardrail classifier.

All recorded mutations were rejected. The first four rows total 122 engineered tampering cases (63 + 18 + 3 + 38). The 18 cross-request rejections test request binding inside the classifier relation, and come from the classifier end-to-end run in exp-V1, not from the composition. The join has its own negative test: the J1 record lists 16 named join-level rejections (`circle-reference-2026-10-28.json`, `.metrics.composition.binding_rejections`). Each case reran the host join with one element changed: four fields of the opened request (prompt, response, system reference, salt); four fields of the expected request (model, nonce, interaction identifier, policy); one public field in each of the three classifier proofs; a missing, duplicated or reordered proof roster; a different request; and a changed caller enrollment (`scripts/check_circle_composed.py`).

The 22 invalid-witness cases are counted separately. Each changes one witness value of an honest 96-byte case and checks that proving fails. For each classifier, five values are targeted: a late input byte, a salt byte, an encoded-padding byte, the active-input mask and the verdict. The MLP adds a byte count, a rounded hidden value and the score; the CNN adds the last convolution accumulator, a pooled maximum and a head bit. Twenty-one of these mutations fail at S-two's constraint check. The twenty-second removes a dense coefficient from the CNN program and is rejected by the caller-enrolled program pin (`scripts/check_circle_classifiers.py`). These single-value mutations test that the listed constraints exist, not that the gadgets are complete. They are not witness-level fuzzing, a malicious prover's search for a satisfying witness of a false statement, or an audit of either proof system, and the circuit-level failure record of Section 4.3 is why that matters.

Sampled peak memory for LLM proving was 103.75 GB of host memory for the CPU run and 8.07 GB of host plus 67.67 GiB of device memory for the GPU run (exp-L1-llm-proving). The record also preserves one failed classifier run, stopped on a storage-quota miscount before the classifier verifier launched (exp-C1-classifier-proving).
